# Frontier Data Views — Handover Brief

A Chrome web app for exploring a whole marketing operation visually: millions of records, many kinds of view, one shared selection, and later an AI agent that reshapes the views around a question.

Research behind every decision here: https://claude.ai/artifact/DReRYyCxXLQufCqmMULD5U (tabs: Research, Inventions, Territories, Marketing KPIs). Read it when a decision below needs more context.

## Rules for Claude (read first, every session)

1. **The owner is not a developer and works from a phone.** Keep replies short and plain. Ask clarifying questions one at a time, numbered (1/3, 2/3…), answerable by number.
2. **Do not guess the owner's setup.** If something about their machine, accounts or files is unknown, ask.
3. **No work references, ever.** This is a personal home project. No real employer, client, financial firm, platform brand or work content in code, data, file names or demo text. All companies, brands, people and copy are invented.
4. **Data is generated by code, never written out by the LLM.** Write generators; never paste large data into files or replies.
5. **Real-world honest.** The demo must be something real data could feed later. Never show a number the data didn't produce. Simulated or projected values look visibly different from recorded ones.
6. **Check the work.** Every milestone ends with its acceptance checks run and reported, including the bad results.

## What it is

Two kinds of thing, nothing else:

- **Makers** create data: the data generator now; later the real-platform ingestion, job forms, the owner's creative editors, and the agent.
- **Views** show data: globe, timeline, creative wall, network, funnel, dashboard, and invented views from the research.

Everything reads from **one shared store** and responds to **one shared selection**. Selecting something in any view highlights it in all of them.

## The fictional company

**Corveth Lyle Partners** — a large, conservative, international B2B professional-services firm. Main marketing team in the US, smaller teams in other regions. It promotes research reports, webinars and conferences, executive commentary, news, newsletters, LinkedIn-style social, paid and organic search, and its websites.

Its data sits in six separate systems that disagree with each other: **CRM, email, web analytics, search, social, events.** (Refer to them by these generic names only; no product names.)

## Platform and stack

- **Target:** desktop Chrome on Mac and PC. Must open from a link with nothing to install.
- **Front end:** Three.js using its WebGPU renderer, with WebGL2 fallback. Plain ES modules; keep the build simple (Vite is fine). One renderer owns the GPU data so records can move between views.
- **Data pipeline:** Python, used **only** to gather and shape data into the store. No modelling or agent logic in Python.
- **Generator:** Python (numpy). It writes **exactly the same output format** the real-data pipeline will write later, so swapping synthetic for real changes no view.
- **Store format:** columnar binary files (one typed array per field) split into tiles by time and region, plus a small JSON manifest, so the browser loads only what's in view. Parquet as the archival copy.

## Milestone 1 — the data generator (build this first)

A seeded script: `python generate.py --seed 20261031 --scale medium`. Same seed, identical bytes.

**Scales:** small ≈ 50k events, medium ≈ 2M events, large ≈ 20M events.

**Entities (all invented):**
- Regions and countries (use ISO country codes; ~60 countries with weighting toward North America, Europe, Asia-Pacific).
- Accounts: client organisations, with sector, size, country, existing-client flag.
- Contacts: role, seniority, account, consent status per channel.
- Campaigns: type (research report, webinar, conference, newsletter, executive commentary, news), owning regional team, dates, budget.
- Content pieces: topic, format, publish date, linked campaign.
- Creative variations: email and social variants per campaign, each with template id and parameters (palette, headline, image style, layout) so a thumbnail can be rendered from it.
- Events (the big table): send, open, click, visit, search click, social impression, social engagement, registration, attendance, download, meeting. Each with timestamp, contact, account, country, channel, campaign, content, creative, and **which platforms recorded it** (bit flags).
- Opportunities: account, value, stage (MQL → SAL → SQL → opportunity → won/lost), created and closed dates, existing-client type (new, renewal, cross-sell).

**Planted patterns** (each must be findable; the checks prove they exist):
1. An August dip every year in most regions.
2. Two countries where web analytics and CRM disagree badly (consent loss on the web side).
3. Email opens inflated by privacy pre-fetching: a share of opens with no human behind them, flagged.
4. One research report whose influence keeps echoing for months after launch.
5. One region where webinar registrations are healthy but attendance collapses.
6. One creative variation that clearly beats its siblings for one audience.
7. One channel whose returns flatten as spend rises.
8. A hidden audience segment that behaves differently from its declared category.
9. Dirty data at 3–5%: duplicates, missing country, impossible dates.

**Thumbnails:** a separate script renders thousands of email and social thumbnails from the creative-variation parameters (templates + seeded variation, invented brand marks), packed into texture atlases with an index. No LLM-drawn images.

**Acceptance checks** (`python check.py`): byte-identical reruns; row counts per scale; every planted pattern detected by a simple query; dirty-data share in range; brand-isolation check (the company name and brand colours appear only in one brand file).

## Milestone 2 — the first view

The globe, with semantic zoom:
- **World:** activity as soft glowing fog over a globe (start with a subdivided icosphere whose faces stand in for countries; real country shapes later).
- **Country:** fog condenses into clusters by campaign.
- **Close:** clusters resolve into individual records, and creative records become their actual thumbnails, a wall sorted by performance.

Plus, from day one: shared selection, a time window control (day, quarter, year, all), and a why-tooltip on every number (which platform counted it, how, and what the other platforms say).

**Acceptance:** loads in Chrome from a local server; medium scale stays above 15 fps on an ordinary laptop (aim for 60); every planted pattern that has a place on the map can be found by zooming and filtering.

## Later milestones (in rough order, confirm before starting each)

3. Timeline and creative-wall views sharing the selection; records fly between views.
4. Platform Parallax: disagreeing sources render blurred.
5. Executive layer: findings first, big numbers, and any view exported as a clean slide image.
6. View specs: every view describable as a small readable JSON file.
7. Agent tools: filter, regroup, lay out, highlight, fly to, annotate; the agent writes view specs and carries the KPI knowledge from the research doc's Marketing KPIs tab.
8. Real-data bridge: Python ingestion from exported files through a mapping file into the same store format.

Invented-view candidates from the research: Question-Shaped Space, Strata, Attention Weather, Ghost Futures, Echo, Fold, Liquid Hierarchy.

## Real-world limits to keep in mind

- Chrome allows about 16 active WebGL contexts per page; avoid many separate canvases.
- Separate rendering libraries each keep their own copy of the data; one owner of the GPU store keeps records movable between views.
- Email opens are unreliable; clicks and later actions are stronger signals.
- Attribution is contested; show how credit changes under different models rather than picking one silently.
